# Sign-In Flow — Do's and Don'ts (Read Before Touching Auth Code)

**Status as of v4.29 (Session 52, confirmed 2026-09-01): working correctly, verified via 2 real-device recordings covering two different failure paths — first-attempt-succeeds-but-data-fetch-stalls, and first-attempt-and-escalation-both-fail.** v4.27 (Session 50) verified cleanly across 3 recordings on the boot/first-tap/success path. A 4th recording (Session 51) surfaced the banner appearing too readily — fixed a skeleton/`calInited` render race and made the banner aware of whether a token already exists — but that fix over-corrected: gating the banner's *detection* on `!Auth.hasValidToken()` silently deleted its recovery path for a stuck *data fetch* after an already-successful sign-in, confirmed by a 5th recording showing 70+ seconds with no banner at all. Session 52 fixed that by keeping detection cause-agnostic and branching only the banner's copy/action on `Auth.hasValidToken()`. Two more recordings then confirmed v4.29 correct on a real device: one showed the banner correctly reading *"Still loading your data… / Retry"* (skips the sign-in overlay, re-fetches directly) when a token already existed, the other showed the tap-anywhere escalation actually firing (its own "Connecting to Google…" toast, the first real-device confirmation of that path) and, once exhausted, the banner correctly reading *"Still connecting to Google… / Retry sign-in"* when no token existed yet — both recovered successfully. This is the end result of a long, expensive investigation (Sessions 35-52, eighteen sessions, including one full 9-session revert in Session 46 after a regression made things measurably worse). Read this section — and the linked sessions if you need the reasoning — before changing anything in `auth.js`, the early first-tap-listener `<script>` in `index.html`, or the stuck-recovery-banner IIFE. If a change is genuinely needed, treat it the way Sessions 50-52 were run: discuss the design first, bump `APP_VERSION` to mark a revert point, and get a real-device screen recording before considering it verified — code review and the sandboxed browser preview cannot exercise the actual Google popup/WebKit behavior this flow depends on. **A specific lesson from Session 52, worth internalizing before touching this banner again**: when a "stuck" signal has more than one legitimate root cause, keep the *detection* cause-agnostic and branch only the *response* (copy, recovery action) on the diagnosis — narrowing detection to "only this one cause" silently deletes recovery for whichever cause you didn't account for.

**The load-bearing files/functions** (nothing here is incidental — each exists to fix a specific, previously-confirmed real bug):
- `auth.js`: `Auth.start()`'s returning-user/new-user fork, `_deferredMode`/`_tokenReady`, `triggerFirstTapSync()`, `Auth.silentRetry()`, `Auth.signIn()`, `Auth.hasValidToken()`, `getAccessToken()`'s deferred-mode wait.
- `index.html`: the early "FIRST-TAP / NEXT-TAP SIGN-IN ESCALATION" `<script>` (placed immediately after `auth.js`'s own `<script>` tag, deliberately outside `DOMContentLoaded`), the `notaFirstTapFired` catch-up listener inside the main `DOMContentLoaded` handler, the `if (isHome() && !calInited) initCalendarSkeleton();` guard (Session 51), and the "STUCK-SIGN-IN RECOVERY BANNER" IIFE including its `isStillStuck()` check.

**Don't:**
- **Don't reintroduce `prompt: 'select_account'` or any interactive Google account-picker.** Tried in Session 40, produced a cascading chain of timeout-mismatch bugs across Sessions 41-43, and was explicitly reverted in Session 44 once `prompt:''` (silent) was confirmed to be both faster and more predictable in every real report gathered. Independently re-proposed and re-rejected later in this same investigation (Session 49's discussion) — the user's own reasoning: it trades "fewer failed attempts" for "the user has to tap Google's own visible UI," which reads as leaving the app, and that's worse than needing an extra tap that stays entirely within Nota.
- **Don't call `Auth.signIn()` from an incidental tap or any background/silent retry path.** `signIn()` unconditionally shows the full-screen "Reconnecting to Google" overlay — correct for its one real caller (the stuck-recovery banner's own dedicated button, a deliberate, explicit user action), wrong for anything meant to be silent. Use `Auth.silentRetry()` (Session 50) for that instead — it has zero UI side effects by design.
- **Don't move the early first-tap-listener `<script>` into the `DOMContentLoaded` handler**, or otherwise delay when it attaches. Session 45/47 confirmed via frame-by-frame screen recording a real ~5s window where the calendar skeleton is visibly painted but a tap does nothing, because `DOMContentLoaded` can't fire until every later `<script>` tag (ui-settings.js/ui-calendar.js/ui-insights.js) finishes loading. This listener is deliberately its own tiny script placed right after `auth.js`'s tag specifically to close that gap — moving it back reopens the exact bug that fix closed.
- **Don't change the stuck-recovery banner's interaction model.** It surfaces a dedicated "Retry sign-in" button and deliberately has no tap-anywhere behavior — this was explicitly locked in by the user earlier in this investigation ("this is ok, don't change it") and reaffirmed again in Session 50 ("keep the banner the same as current"). A prior experiment that added tap-anywhere-on-the-banner was part of what Session 46 had to revert.
- **Don't retune a single timeout constant in isolation.** Sessions 37, 38, 41, 42, and 43 each individually "fixed" a mismatched timeout and each time a different, untouched link in the same nested chain (`requestToken()` → `getAccessToken()`'s wait → `loadHistData()`'s `fetchWithTimeout` → `fetchCurrentMonth()`/`fetchCurrentMonthFresh()`'s own hardcoded timeout) became the new binding constraint, sometimes making the real, measured experience worse. If a timeout genuinely needs to change, trace every layer that wraps it first, per Session 43's lesson.
- **Don't assume WebKit/iOS-PWA behavior without a real-device test.** Several bugs in this history (Sessions 34, 35, 39) came from behavior that only reproduces on an installed Home Screen app, not a normal browser tab or desktop — code review and this project's sandboxed browser preview cannot exercise Google's actual popup relay or WebKit's standalone-runtime quirks.

**Do:**
- **Do treat any future change here as its own mini-experiment**: discuss the design before touching code, bump `APP_VERSION` to mark an explicit revert point, and verify with a real-device screen recording (not just "it didn't crash in the preview") before considering it done. This is the exact process that finally produced a confirmed-clean result in Session 50, after nine consecutive sessions (37-45) of well-reasoned individual fixes that didn't actually improve the measured, real-device experience.
- **Do keep `Auth.silentRetry()` and `Auth.signIn()` distinct** — one silent (no UI), one interactive (full overlay, only from a deliberate user action) — rather than collapsing them back into one function "for simplicity." That distinction is precisely what let Session 50's redesign avoid disrupting the user with a visible Google-adjacent overlay on an ordinary, incidental tap.
- **Do re-read the full session history (Sessions 35-50) before making a structural change** — not just this summary — since the reasoning behind several non-obvious decisions (e.g. why `select_account` was tried and rejected twice, why nine sessions of fixes were reverted wholesale in Session 46) lives there, not in the code comments alone.
